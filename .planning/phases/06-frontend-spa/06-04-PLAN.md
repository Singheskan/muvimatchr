<objective>
Make the router obey the server, and build the waiting screen.

Two things land here. First, D-04's route guards: every session route reads live status on mount
and redirects the user to the screen the server says they belong on. That is the entire mechanism
behind RSLT-01 and ROADMAP Success Criterion 2 - opening a link cold after everyone finished lands
directly on results, with no dead end, blank screen or manual refresh. Second, D-10's named waiting
roster wired to the Phase 5 STOMP topic, implementing the client half of the reconnect-reconcile
contract Phase 5 built the server half of.

Purpose: this is where the "looks done but isn't" failure modes live. A waiting screen that only
ever updates from a WebSocket message is indistinguishable from a working one until someone's phone
locks - and then it is stuck forever.

Output: `resolveScreen`, `useRouteGuard`, `useSessionSocket`, and the waiting screen at
`/s/:code/wait`.
</objective>

**frontend/src/routing/resolveScreen.ts.** Export
`export type Screen = 'join' | 'swipe' | 'wait' | 'results'` and the pure function
`resolveScreen({ hasToken, status, myVotedCount }: { hasToken: boolean; status: VoteStatusResponse | null; myVotedCount: number }): Screen`
with these rules, in order:
1. `!hasToken` returns `'join'`.
2. `status === null` returns `'join'`.
3. `status.isComplete` returns `'results'`.
4. `status.deckSize > 0 && myVotedCount >= status.deckSize` returns `'wait'`.
5. otherwise `'swipe'`.

Rule 3 reads the server's completion flag and nothing else. Do not derive completion by comparing
the status response's two participant-count fields, from roster flags, or from a local vote tally -
that is prohibition P-02, and it is the precise failure the prior prototype shipped. Rule 4's `deckSize > 0`
conjunct mirrors the same guard `MatchAggregationService.computeStatus` carries: a never-pinned
session must not read as finished.

**frontend/src/routing/useRouteGuard.ts.** Export
`useRouteGuard(code: string | undefined, currentScreen: Screen, input: { hasToken: boolean; status: VoteStatusResponse | null; myVotedCount: number; ready: boolean })`.
In a `useEffect`: return immediately unless `ready` and `code` are truthy; compute
`resolveScreen(input)`; if it differs from `currentScreen`, `navigate` to the matching path
(`'join'` maps to `/s/${code}`, the others to `/s/${code}/${screen}`) with `{ replace: true }`,
preserving the existing query string so the token survives the redirect. Effect dependencies are
the resolved screen, `currentScreen`, `code` and `ready` only - not the whole status object, so a
status refetch that changes nothing does not re-fire the navigation.

The `ready` flag exists so no screen redirects while its own data is still loading; without it every
route would flash through `'join'` on first paint, because status starts null.

Preserving the query string is load-bearing: the participant token lives there (D-05), so a redirect
that drops it logs the user out mid-flow.

**frontend/src/realtime/useSessionSocket.ts.** Export
`export type ConnectionState = 'connecting' | 'connected' | 'reconnecting'` and
`useSessionSocket(sessionId: string | undefined, onFrame: () => void): ConnectionState`.

Build the client from `@stomp/stompjs`:
- `brokerURL` derived from the current page origin: `wss` when `window.location.protocol` is `https:`, otherwise `ws`, plus `window.location.host`, plus `/ws`. Same-origin by construction, which is why D-01's single-JAR deployment needs no origin configuration here.
- `reconnectDelay: 5000`, `heartbeatIncoming: 10000`, `heartbeatOutgoing: 10000`.
- Do not add a fallback transport shim; STACK.md rejects one for this browser target and Phase 5's endpoint is registered without it, so the client must connect natively.

Hold `onFrame` in a ref that an effect keeps current, so the socket effect's dependency array is
`[sessionId]` alone. Without that, every parent re-render would tear the socket down and rebuild it.

In `onConnect`: set state `'connected'`, call `onFrameRef.current()` (this is the reconnect-reconcile
trigger - it fires on the very first connect and on every reconnect), then create the subscription:
`subscriptionRef.current = client.subscribe('/topic/session/' + sessionId, () => onFrameRef.current())`.
This must be the only `client.subscribe` call site in the file. Subscribing anywhere else - at
activation, in a separate effect, or on a state change - is the documented stompjs duplicate-delivery
hazard flagged as an open item in STATE.md, because the library re-runs `onConnect` on every
reconnect and does not restore or de-duplicate prior subscriptions.

In `onWebSocketClose` and `onStompError`: set state `'reconnecting'` and set
`subscriptionRef.current = null` (the old subscription object is dead with the connection and must
not be reused).

In the effect cleanup: `subscriptionRef.current?.unsubscribe()`, null the ref, then
`client.deactivate()`.

Deliberately do NOT deserialize or apply the inbound payload. The handler takes no argument, ignores
what arrived entirely, and just re-triggers a REST read. Phase 5 proved the pushed object is
identical to the REST body, so applying it directly would work today - but "the socket is a signal
to re-read, never a carrier of truth" (prohibition P-04, ARCHITECTURE.md Pattern 3) is the invariant
that makes a missed push harmless, and it holds only if there is exactly one path by which displayed
state arrives.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `/ws` STOMP endpoint | A WebSocket connection and topic subscription, deliberately unauthenticated at the frame level per Phase 5 D-01 |
| browser -> `/api/sessions/{sessionId}/votes/status` and `/roster` | Token-authenticated REST reads that are the sole source of displayed state |
| client-side router -> screen selection | Untrusted URL determines which screen renders, but not what data is readable |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-15 | Tampering | A client treating a WebSocket frame as authoritative state | high | mitigate | `useSessionSocket`'s handler ignores the frame payload entirely and only invalidates the REST queries; displayed state has exactly one source. Enforced by a negative grep gate rejecting any frame-body read in that file, and by the reconnect test asserting `onFrame` fires on every connect before any frame arrives. |
| T-06-16 | Denial of Service | `@stomp/stompjs` auto-reconnect stacking duplicate subscriptions | medium | mitigate | Exactly one `client.subscribe` call site, placed inside `onConnect`; the returned subscription is nulled on close and unsubscribed on cleanup, and the client is deactivated on unmount. Asserted by a connect-disconnect-reconnect unit test and by a grep gate pinning the subscribe call count to one. This closes the stompjs review item STATE.md has carried open since Phase 5 planning. |
| T-06-17 | Elevation of Privilege | Client-side route guard mistaken for an access control | medium | accept | D-04 states routing is presentation only. Every screen's data still comes from token-authenticated endpoints that enforce membership server-side, so bypassing the guard by typing a URL reveals nothing: the underlying fetches return 401 or 404 and `resolveScreen` sends the user back to the join screen. No client-side check is relied on for confidentiality. |
| T-06-18 | Information Disclosure | Unauthenticated subscription to `/topic/session/{sessionId}` | medium | accept | Pre-existing and deliberately deferred in 05-CONTEXT.md D-01. The session id is a version-4 UUID and this phase adds no anonymous path to obtain one (see 06-01 threat T-06-02, which token-gates the join-code lookup). Carried forward for the pre-public-deploy hardening pass alongside the standing rate-limiting item, not newly introduced here. |
| T-06-19 | Information Disclosure | Participant display names rendered on the waiting screen | low | mitigate | Names come only from the membership-gated roster endpoint (06-02 threat T-06-06) and render through ordinary JSX text interpolation; a participant-chosen display name is untrusted input and is never injected as markup. |
