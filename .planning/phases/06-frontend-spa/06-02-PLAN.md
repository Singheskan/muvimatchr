<objective>
Add the one backend read the waiting screen needs and today cannot get: a named participant roster
with per-person voting progress.

`VoteStatusResponse` carries only `activeCount` and `finishedCount`. D-10 requires the waiting
screen to read like a named roster ("Alex done, Jordan done, Sam waiting"), which needs display
names and per-participant progress. Rather than widening `VoteStatusResponse` - the exact payload
Phase 5 proved byte-identical across REST and WebSocket, with two existing tests asserting that
parity - this plan adds a separate, additive endpoint and leaves the Phase 4/5 contract frozen.

Purpose: unblock D-10 without disturbing the REST/WebSocket parity invariant Phase 5 established.
Output: `GET /api/sessions/{sessionId}/votes/roster`.
</objective>

**ParticipantRepository.** Add the derived query
`fun findBySession_IdOrderByCreatedAtAsc(sessionId: UUID): List<Participant>`. Join order is the
roster's display order and must come from the database, not from a Kotlin re-sort.

**VoteRepository.** Add a native query
`fun findVoteCountsByParticipant(@Param("sessionId") sessionId: UUID): List<Array<Any>>`
selecting `v.participant_id, COUNT(*)` from `vote` where
`v.session_id = CAST(:sessionId AS uuid)`, grouped by `v.participant_id`. Follow the file's
existing conventions exactly: named `@Param` bindings only, the `CAST(:sessionId AS uuid)` idiom,
and never string interpolation into the query text. This query counts all votes regardless of
choice - a PASS is progress through the deck just as much as a LIKE - so it must not filter on
`choice`, in deliberate contrast to `findLikeCountsBySession` which does.

**MatchAggregationService.** Inject `ParticipantRepository` alongside the existing three
dependencies and add `fun computeRoster(sessionId: UUID): SessionRoster` which:

1. loads the session the same way `computeStatus` does, throwing the same 404 `ResponseStatusException` when absent;
2. computes `deckSize` as `sessionService.pinnedMovies(session).size` - the pinned snapshot, never a catalog re-query, matching the existing Pitfall-D guard in `computeStatus`;
3. calls `voteRepository.findActiveParticipantIds(sessionId, inactivityTimeoutSeconds)` and turns the result into a `Set<UUID>`. Call that method; do not restate the inactivity rule here. The fallback expression inside that repository query (last vote time, falling back to join time) is D-06 stated exactly once, and a second copy anywhere in this service would be free to drift from the one the completion arithmetic uses;
4. builds a `Map<UUID, Int>` of voted counts from `findVoteCountsByParticipant`, coercing each row's `Number` values the same way `perMovieLikeCounts` already does;
5. maps `participantRepository.findBySession_IdOrderByCreatedAtAsc(sessionId)` into `ParticipantProgress(participantId = p.id!!, displayName = p.displayName, votedCount = counts[p.id] ?: 0, isFinished = deckSize > 0 && votedCount >= deckSize, isActive = p.id in activeIds)`.

The `deckSize > 0` conjunct is the same load-bearing guard already commented in `computeStatus`;
without it a never-pinned session reports every zero-vote participant as finished.

Add the two domain data classes to the same file, next to `SessionVoteStatus`:
`data class ParticipantProgress(val participantId: UUID, val displayName: String, val votedCount: Int, val isFinished: Boolean, val isActive: Boolean)`
and
`data class SessionRoster(val sessionId: UUID, val deckSize: Int, val participants: List<ParticipantProgress>)`.

Hold no state: this method caches nothing and stores nothing, exactly like the rest of the class.
