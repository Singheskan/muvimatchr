<objective>
Wire the entire "create a session, join it, get a token, resolve who-am-I by that token" path end-to-end against the Phase 1 schema: a new Flyway migration, the Participant token column, the join-code and token-issuance services, the custom bearer-token resolver, and both new REST controllers — proven by one real MockMvc-against-Postgres integration test, not mocks.

Purpose: this is the phase's tracer slice. This codebase's first REST controller layer and first auth mechanism both land in this plan, so its job is to prove the whole novel architecture — DB-level join-code collision retry, SecureRandom+SHA-256 token issuance, hash-at-rest storage, and a custom `HandlerMethodArgumentResolver` standing in for Spring Security — before Plan 02-02 spends any effort hardening edge cases on top of it. It is production-quality, not a prototype: every file here is the real, final artifact Phase 4 (voting) and Phase 6 (frontend) build on.

Note on task shape: this plan's Task 1 touches more files than the "≤5 files" default guideline, because this genuinely is the thinnest path through every layer this phase introduces (migration, entity, two repositories, two services, two controllers, one test) in a codebase where none of those layers existed yet — splitting it further would produce non-functional intermediate states (e.g. a controller with no service to call), not smaller working slices. Per-file line counts are small; RESEARCH.md/02-PATTERNS.md already designed the exact shape of every new file, so this is adaptation, not invention.

Note on a deliberate deviation from 02-RESEARCH.md's illustrative code: RESEARCH.md's Pattern 1 example wraps the join-code retry loop in a single `@Transactional` method calling `saveAndFlush` per attempt. That shape is broken on PostgreSQL specifically — once one statement in a transaction fails, Postgres aborts the *entire* transaction ("current transaction is aborted, commands ignored until end of transaction block"), so a second `saveAndFlush` attempt inside the same `@Transactional` boundary after the first's constraint violation would fail with that abort error, not retry cleanly. `SessionService.createSession()` in this plan therefore carries NO `@Transactional` of its own, and each retry attempt calls the plain `save()` Spring Data method (itself individually transactional), so each attempt gets its own transaction — exactly how Phase 1's own `SessionRepositoryTest` already proves two sequential `saveAndFlush` calls behave (first commits, second fails cleanly), since that test also has no surrounding `@Transactional`.

Output: session creation, participant join with server-issued token, bearer-token resolution/resume, all four wired end-to-end and covered by one integration test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> POST /api/sessions | Untrusted caller creates a new session; unauthenticated by design (session creation has no credential to check yet) |
| Client -> POST /api/sessions/{joinCode}/participants | Untrusted caller supplies joinCode + displayName; this IS the credential-issuance boundary — the response is the only time the raw token ever leaves the server |
| Client -> GET /api/sessions/{sessionId}/participants/me | Untrusted caller supplies `Authorization: Bearer <token>`; this is the phase's sole access-control check |
| Client's saved resume link (URL) | The token embedded once in `resumeUrl` crosses into browser history / bookmarks — an inherently less-controlled medium than a header |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Spoofing | `TokenService` (issuance) + `CurrentParticipantArgumentResolver` (resolution) | high | mitigate | 256-bit `SecureRandom` token, SHA-256 hash-at-rest via `MessageDigest`, unique index `uq_participant_token_hash`, equality lookup via `ParticipantRepository.findByTokenHash` — brute-forcing or enumerating a 256-bit space is computationally infeasible |
| T-02-02 | Information Disclosure | `resumeUrl` (token embedded in a URL) | medium | mitigate | The token appears in `resumeUrl` exactly once by design, an accepted tradeoff per D-02; `GET .../me` reads the token exclusively from the `Authorization: Bearer` header — no endpoint in this phase accepts the token as a query parameter |
| T-02-03 | Tampering | `SessionRepository.findByJoinCode` / `ParticipantRepository.findByTokenHash` | low | mitigate | Both are Spring-Data-derived query methods with no native SQL — parameter binding is handled entirely by JPA/Hibernate, no string interpolation is possible |
| T-02-04 | Repudiation | No request/audit logging of participant identity this phase | low | accept | Out of scope for v1 per REQUIREMENTS.md (no accounts/audit requirement); revisit only if abuse reports require it |
| T-02-05 | Elevation of Privilege | No token revocation/expiry mechanism (intentionally long-lived) | medium | accept | Deliberate scope decision per SESH-05's "resume later without losing progress" and D-04 (no lock/state machine this phase); flagged explicitly here so it is not silently forgotten later |
| T-02-06 | Tampering | `Participant.tokenHash` column / migration V4 | low | mitigate | `VARCHAR(64)` exactly fits a hex-encoded SHA-256 digest, `NOT NULL` enforced at the DB level, `UNIQUE` index prevents any hash from resolving to two different participants |
