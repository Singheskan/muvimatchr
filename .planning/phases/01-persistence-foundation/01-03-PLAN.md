    Create `src/main/kotlin/org/example/muvimatchr/voting/VoteRepository.kt` as `interface VoteRepository : JpaRepository<Vote, UUID>` plus one method `upsertVote`, copied from RESEARCH.md Pattern 4. The statement inserts into `vote (id, session_id, participant_id, movie_id, choice, voted_at)` and carries `ON CONFLICT (session_id, participant_id, movie_id) DO UPDATE SET choice = EXCLUDED.choice, voted_at = now()`. The conflict target must name exactly the three columns the unique constraint covers, or Postgres rejects the statement at execution time. Every one of the five values reaching the SQL — id, sessionId, participantId, movieId, choice — arrives through a `@Param`-annotated named parameter and appears in the statement only as a named placeholder. Do not build any part of this SQL by interpolating a Kotlin value into the string, even though no HTTP layer exercises it yet: Phase 4 will call this method with a movie id and a choice that originate from a user's swipe, so the statement has to be injection-safe by construction now rather than retrofitted later. Wrap the two UUID placeholders that Postgres cannot infer a type for in an explicit `CAST(... AS uuid)`, per the Spring Data JPA native-query UUID binding issue RESEARCH.md cites — the cast applies to the bound parameter and is not string concatenation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Caller-supplied values → native SQL statement | `VoteRepository.upsertVote` is the only hand-written SQL in the project. Phase 4 will call it with a movie id and a choice that originate from a user's swipe, so it crosses from caller-controlled data into a database statement. |
| Concurrent writers → vote table | The same participant can submit the same vote more than once — a double-tap, a retry after a dropped connection, a rejoin from another device. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Tampering | `VoteRepository.upsertVote` native `@Query` | high | mitigate | Bind all five values through `@Param`-annotated named parameters; the statement contains only named placeholders and no Kotlin string-template interpolation. The explicit `CAST(:param AS uuid)` wraps a bound parameter and is not concatenation. Enforced mechanically by two gates in Task 2: an exact count of five `@Param` annotations, and a negative assertion that the file contains no string-template interpolation at all. This is the one V5 Input Validation concern RESEARCH.md's Security Domain flags as partial for this phase; it is mitigated now rather than when Phase 4 first sends user-influenced values through it. |
| T-01-05 | Tampering | Vote write path under concurrent submissions | medium | mitigate | Enforce the constraint in the database (`uq_vote_session_participant_movie`) and write through `INSERT ... ON CONFLICT DO UPDATE`, which resolves the conflict atomically inside one statement. A read-then-write "find or create" in application code has a time-of-check-to-time-of-use window in which two concurrent submissions from the same participant both see no existing row — the exact class of bug that broke the prior prototype's vote aggregation. Task 2's third test proves the constraint holds independently of whether the upsert path was used, so an application-level bypass cannot silently create a duplicate. |
</threat_model>
