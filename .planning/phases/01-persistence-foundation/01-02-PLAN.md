<objective>
Prove the entire persistence stack end-to-end on one entity: a Flyway-created `session` table, a `Session` JPA entity validated against it, a Spring Data repository, and a literal application restart against a real PostgreSQL instance that reads the row back.

Purpose: this is the phase's tracer slice. It is deliberately one entity and one assertion wide, because its job is to prove the architecture — Flyway owns the schema, Hibernate only validates it, and a genuinely new application process reconnecting to the same database sees the same rows — before Participant and Vote are built on top of it in Plan 01-03. It is production-quality, not a prototype: `Session`, `SessionRepository` and `V1__create_session.sql` are the real, final artifacts every later phase inherits. If the composed restart mechanism does not hold (RESEARCH.md Assumption A1), this plan is where that is discovered — after one commit, not after ten.

Output: the `session` table, its entity and repository, the D-03 restart-survival proof, the shared Testcontainers fixture, and the join-code unique-constraint proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application entity mappings → database schema | Two independent descriptions of the same tables. If they are allowed to disagree, one of them silently rewrites the other. |
| Flyway migration files → deployed schema | Version-controlled DDL is the only sanctioned path by which the schema changes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-02 | Tampering | Hibernate schema management at application startup | medium | mitigate | Set `spring.jpa.hibernate.ddl-auto` to `validate` in both `application.properties` (Plan 01-01) and the explicit property list `RestartSurvivalTest` hands to each `SpringApplicationBuilder`. Under `validate`, a divergence between `Session.kt` and `V1__create_session.sql` fails context startup loudly instead of letting Hibernate mutate the live schema to match itself. The generate-and-mutate settings for that property are forbidden by `.planning/research/STACK.md`; the acceptance criteria in Plan 01-01 pin the property to a single non-comment line so no second value can shadow it. |
| T-01-03 | Repudiation | Schema change history | low | mitigate | Every schema change is a numbered, version-controlled file under `src/main/resources/db/migration/`, and Flyway records each application in `flyway_schema_history`. Task 1 asserts that history row count is unchanged across the restart, which proves both that the record exists and that a second startup did not silently re-run DDL. Hand-applied SQL leaves no such trail and is what this arrangement replaces. |
</threat_model>
