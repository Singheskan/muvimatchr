<objective>
Cache TMDB's two reference catalogs — the movie genre list and the per-region watch-provider list — in their own long-lived tables, expose them so a client can build a filter UI without hardcoding ids, and use them as the validation domain for every filter value the application forwards upstream.

Purpose: two distinct jobs that share one data source, which is why they share a plan. The first is D-08's second half: these catalogs are effectively static for weeks, so re-fetching them per deck request would be the exact anti-pattern RESEARCH.md flags — they get their own tables and their own much longer TTL, separate from the 6-hour deck TTL. The second is ASVS V5 as RESEARCH.md's Security Domain specifies it: a genre id or a provider id is an untrusted integer that this application concatenates into a third-party URL, and "is it a real genre" is only answerable once the genre list is cached locally. Building the cache without then using it for validation would leave the more valuable half undone.

This plan is Wave 3 because it adds Flyway migration V7 and because its validation call site sits inside `SessionController`, which Plan 03-02 creates the filter handlers in. Both are ordering constraints on shared artifacts, not sizing.

Output: `genre` and `watch_provider` tables with atomic per-row upserts, a lazy-on-miss refresh service with a configurable long TTL, two authenticated reference endpoints, and rejection of unknown genre and provider ids before any outbound call or any stored write.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> GET /api/catalog/genres, GET /api/catalog/watch-providers | Untrusted caller reads reference data whose population may trigger an outbound call |
| Client -> genre query parameter on the deck endpoint | An untrusted integer that would otherwise be concatenated into a third-party URL |
| Client -> provider ids on session creation and filter replacement | Untrusted integers that become persisted state and are later forwarded upstream |
| Application -> api.themoviedb.org (reference endpoints) | Two additional outbound call sites sharing the one credential |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-16 | Tampering | Unvalidated `genre`/provider ids forwarded into the outbound TMDB URL | high | mitigate | `requireKnownGenre` and `requireKnownProviders` check every value against the locally cached catalogue before any outbound call or stored write and reject with 400; values are still attached via `UriBuilder.queryParam` so encoding is handled separately from validity. This closes the V5 gap Plan 03-01's register recorded as deferred to this plan |
| T-03-17 | Denial of Service | Unauthenticated reference endpoints used to drive outbound calls | medium | mitigate | Both handlers require `@CurrentParticipant`; the seven-day reference TTL bounds outbound volume to one call per scope per week regardless of caller volume |
| T-03-18 | Information Disclosure | Internal row identifiers leaked through the reference responses | low | mitigate | `GenreResponse` and `WatchProviderResponse` carry the TMDB identifier only; the internal UUID primary key is never mapped into a response type |
| T-03-19 | Tampering | Concurrent reference refresh producing duplicate or partially-overwritten rows | medium | mitigate | Every reference write is a single native `INSERT ... ON CONFLICT DO UPDATE` keyed by the same uniqueness the migration declares — `(tmdb_id)` for genres and the composite `(region, tmdb_id)` for providers |
| T-03-20 | Denial of Service | A reference refresh failing while a deck request is in flight | medium | accept | An exhausted-retry failure during a reference fetch propagates as an error for that request. The deck's own degradation path (serve last known cache) is D-04's scope and lands in Plan 03-05; extending stale-serve to reference data is not required by any decision and is recorded here rather than silently assumed |
| T-03-21 | Spoofing | Reference endpoints accepting a token from any session | low | accept | Deliberate — this data is not session-scoped, so binding it to one session would add a check with no protective value; a valid participant token is the whole requirement |
