<objective>
Complete both halves of the phase's provider story: filter the deck by the session's streaming-provider selection in its region (D-09, CTLG-03), and attach each returned movie's own resolved availability list to the deck response (D-10, the last open piece of CTLG-01).

Purpose: these are one plan because they are one data flow and one cost decision. The filter is free — TMDB's `with_watch_providers` takes the whole selection as a single comma-separated value, so a multi-provider session still costs one request. The per-movie availability display is not free: it is one additional request per movie, up to about twenty per refresh. That cost is only acceptable because it is paid on the refresh path exclusively and amortised by the six-hour deck TTL, which means the same code change has to establish both the fan-out and the guarantee that it never happens on a cache hit. Splitting them would leave the guarantee untested against the thing it constrains.

The deck's region and provider selection are read from the session row, never from the request. That is what makes the filter a group-level decision rather than something each participant's client could disagree about, and it is why Plan 03-02 put both fields on `Session` in the first place.

Output: a fourth client call method, bounded-concurrency availability resolution inside the refresh path, session-sourced filtering on the deck endpoint, and per-movie provider data in the deck response.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Application -> api.themoviedb.org (per-title availability) | A new outbound call site issued up to twenty times per refresh, sharing the one credential |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-22 | Denial of Service | Per-movie availability fan-out amplifying one user action into ~20 upstream requests | high | mitigate | Lookups occur only on the refresh branch, never on the cache-hit branch (grep-gated to a single call site, plus a request-count-delta test asserting exactly 0 on a hit); concurrency is bounded by a configurable semaphore defaulting to 8, sized against TMDB's published soft ceiling; the six-hour deck TTL bounds refreshes to one per filter combination per window |
| T-03-23 | Information Disclosure | One region's availability data served to a session in another region via a shared cache row | high | mitigate | The region participates in the cache key (established in Plan 03-01 specifically to prevent this), and resolution is an exact-key lookup on the requested region with no fallback; a test asserts two regions produce two rows carrying their own data |
| T-03-24 | Tampering | Stored provider ids and region reaching the outbound TMDB URL | medium | mitigate | Values were validated against the cached reference catalogues at write time in Plan 03-03 and are attached via `UriBuilder.queryParam`; the deck reads them from the session row rather than from the request, so no request-time value reaches the URL at all |
| T-03-25 | Spoofing | A participant tailoring their own deck away from the group's selection | medium | mitigate | The deck handler exposes no region or provider request parameter, grep-gated; both values come from the shared session row |
| T-03-26 | Denial of Service | One failing availability lookup aborting an otherwise complete deck refresh | medium | mitigate | Each lookup is individually wrapped: an exhausted-retry failure yields an empty provider list for that movie only, and the deck is still returned |
| T-03-27 | Information Disclosure | Availability data implying a false claim about where a title can be watched | medium | mitigate | Exact-region resolution with no fallback; an absent region entry yields an empty list and a null link rather than a substituted region's data; a grep gate rejects first-available-region selection expressions |
