<objective>
Prove the entire TMDB catalog architecture end-to-end on one thin path: a genre-filtered deck request travels from a REST endpoint, through a cache-freshness check, out to TMDB over an authenticated WebClient, back into a Postgres JSONB cache row, and out to the caller as the app's own DTO — with the credential never leaving the server.

Purpose: this is the phase's tracer slice. Every layer this phase introduces is novel to this codebase — the first outbound HTTP client, the first external-API DTO translation, the first JSONB column, the first TTL cache, the first fake-HTTP-server test harness. Wiring one real path through all of them first means an architectural dead end (Boot 4's `WebClient.Builder` auto-configuration relocation, a Hibernate JSONB mapping that `ddl-auto=validate` rejects, a mockwebserver3 API shape that does not match expectation) surfaces after one commit rather than after four plans of horizontal layers are already committed on top of it.

This is production-quality code, not a prototype: `CacheKey.buildDeckCacheKey` takes its full final signature (genre + provider list + region) in this plan even though the tracer only ever passes an empty provider list, because D-07 rates the cache key as costly to change and re-keying it in a later plan would invalidate this plan's own CTLG-04 cache-hit assertions. Likewise `DeckMovieResponse` carries its `providers` field from the start (empty in this plan, populated by Plan 03-04 per D-10) so the response contract never changes shape underneath Phase 6.

Deliberate deviations from `03-RESEARCH.md`'s illustrative code, both load-bearing:

1. **`tmdb.api.read-access-token` gets an empty default (`${TMDB_API_TOKEN:}`), not a bare `${TMDB_API_TOKEN}`.** RESEARCH.md Pattern 2 shows the bare form. That form makes Spring placeholder resolution fail at context startup whenever the environment variable is absent — and it is absent on this machine (RESEARCH.md "Environment Availability"). A bare placeholder would therefore break every pre-existing Phase 1 and Phase 2 test, not just this phase's. The empty default keeps the context startable; the tests that need a credential inject their own via dynamic properties.

2. **The service bridges into the suspend client with `runBlocking`, it does not become reactive.** This application is Spring MVC on the servlet stack; `spring-boot-starter-webclient` supplies an outbound client only, no reactive server. Blocking a servlet request thread on an outbound call is exactly what an MVC controller already does for every JDBC call. Coroutines are still worth their dependency because Plan 03-04's D-10 batch resolves up to 20 per-movie provider lookups concurrently, which is awkward without them.

Two open questions 03-RESEARCH.md explicitly routed to the planner are resolved here rather than left to the executor:

- **Assumption A3 — JSONB deck row versus a normalized `cached_movie` table plus a join table.** Resolved: JSONB only, no normalized movie table in this phase. A3 asked for an up-front decision because a later need to query a single movie by TMDB id independent of a filter combination would otherwise force a follow-up migration. That need does not arise: Phase 1's `vote` table already carries `movie_id BIGINT` as its own column (migration V3), so Phase 4's vote-by-movie lookups key off the vote table and never need a movie-entity join. One row per filter combination is also the exact shape D-07's cache semantics describe, so the simpler design is the one that matches the decision rather than merely the one that is less work.
- **Assumption A4 — endpoint placement.** Adopted as recommended: the deck lives under the existing `/api/sessions/{sessionId}/...` prefix, matching `SessionController` and `ParticipantController`, and reads session-scoped state server-side rather than accepting it as a client parameter.

Output: a working `GET /api/sessions/{sessionId}/deck` backed by real TMDB `/discover/movie` data (faked in tests, real at runtime), a filter-combo-keyed Postgres cache with a proven TTL and a proven atomic upsert, and a test that proves the credential never reaches the caller.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> GET /api/sessions/{sessionId}/deck | Untrusted caller supplies a session id, an optional genre value, and a bearer token; the only access control on the deck is the Phase 2 participant token |
| Application -> api.themoviedb.org | Outbound boundary where the TMDB read-access token is presented; everything on the far side is a third party |
| Application -> deck_cache_entry (Postgres) | Upstream JSON is persisted verbatim into a JSONB column and later re-served to callers |
| Application -> application logs | Any header/request logging on the outbound client would cross the credential into an unprotected medium |
