<objective>
Close the two behaviours that only matter when things go wrong: what a deck request does when TMDB is unreachable (D-04), and what it does when a filter combination barely matches anything (D-06).

Purpose: both are the difference between a demo and something usable. D-04's rule is a three-step ladder — retry, then serve whatever is cached even if stale, then and only then fail — and each rung has a distinct observable outcome, so each needs its own test. D-06's rule exists because a two-movie deck is a worse experience than an honest "try broader filters", and because the failure mode it prevents is the one a user cannot detect: a filter that looks like it worked while quietly showing the wrong thing.

Both land after Plan 03-04 because both wrap the refresh path that plan finished. Adding an outage fallback before per-movie availability resolution existed would have meant writing the fallback twice.

This plan is also where the phase's live-credential verifications are recorded. Every automated test in Phase 3 runs against a local fake HTTP server, which proves the integration logic and proves nothing about live TMDB. ROADMAP criterion 1 says "real TMDB titles", and that word is only testable by a human with a credential — so it is captured as a `<human-check>` for the end-of-phase batch rather than silently claimed by a green test suite.

Output: retry-then-stale-then-fail degradation with an honest stale marker, the discriminated insufficient-results response, and the two human verifications this phase cannot automate.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| api.themoviedb.org -> application (failure modes) | Upstream errors, timeouts and rate-limit responses now drive an application decision about what to serve |
| deck_cache_entry (past-TTL row) -> deck response | Data of unbounded age is deliberately re-served during an outage |
| Application -> caller (degraded response) | The caller must be able to distinguish a degraded answer from a current one |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-28 | Tampering | Poisoned cache row written on a failed refresh | high | mitigate | The failure path writes nothing; `upsertDeck` is called from exactly one place, on the success path, grep-gated, and a test asserts a zero row count after a failed cold refresh. Without this, one transient outage would persist an empty deck served as legitimate for a full TTL window |
| T-03-29 | Information Disclosure | Stale availability data presented as current | medium | mitigate | `stale = true` propagates from `DeckResult` into `DeckResponse`, asserted at the endpoint level; a fresh cache hit carries `stale = false`, so the marker means degraded specifically and not merely cached |
| T-03-30 | Denial of Service | Upstream outage becoming a total application outage | medium | mitigate | D-04's ladder serves the last known deck for the same filter combination rather than failing, so an outage degrades rather than breaks; only a combination never successfully fetched fails, and it fails explicitly |
| T-03-31 | Denial of Service | Repeated requests for a sparse filter combination hammering TMDB | low | mitigate | Sparse combinations are cached under the same rule as any other; the sparse determination happens when shaping the response, so a retry inside the TTL costs zero upstream requests |
| T-03-32 | Information Disclosure | Error response leaking upstream detail or credential material | medium | mitigate | The 503 carries a fixed application-authored message and never interpolates the upstream response body, upstream headers, or the request URL — the URL would carry the filter values and the client is configured with the credential as a default header |
| T-03-33 | Spoofing | A degraded response substituting another filter combination's deck | medium | mitigate | The fallback reuses the row already loaded for this exact cache key; no lookup by any other key exists on the failure path, and this plan's prohibition covers the widening case |

</threat_model>
