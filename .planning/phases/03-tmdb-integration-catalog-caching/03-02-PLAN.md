<objective>
Give a `Session` the two pieces of persisted filter state the deck needs — a region and a set of streaming-provider ids — settable optionally at creation and replaceable afterwards by any participant of that session.

Purpose: Plan 03-04 turns these two fields into TMDB's `watch_region` and `with_watch_providers` parameters. Storing them on the session rather than accepting them per-request is what makes region-aware provider filtering a group-level decision rather than something each participant's client could disagree about, and it is what D-01/D-02/D-09 lock in. Doing it in its own plan keeps it out of the catalog package entirely: this plan touches only `session/` and one new migration.

Why this is Wave 2 rather than running beside the tracer: it shares no source file with Plan 03-01 and could otherwise run in parallel, but it adds a Flyway migration. Two plans in one wave each adding a migration can land in either order, and a lower-numbered migration arriving after a higher-numbered one already ran is exactly the out-of-order condition Flyway refuses on a persistent database — which is what the developer's local Postgres is. Sequencing the migration-adding plans is a correctness constraint, not a sizing one.

Output: `session.region` and `session.provider_ids` columns, the matching entity state, an optional creation-time selection, and `GET`/`PUT /api/sessions/{sessionId}/filters` guarded only by session membership.
</objective>

<assumption_delta_decision>
**Noun under review:** the session's streaming-provider selection.

Earlier phase framing (ROADMAP, and this phase's own research before 2026-09-04) implicitly treated it as singular — "the session's provider", one `providerId`. CONTEXT.md D-09 makes it plural and optional: "a session can select zero, one, or multiple providers". CONTEXT.md D-01/D-02 likewise make region optional-with-default rather than required.

**Decision: `promote`.** The plural, list-shaped noun becomes the primary and only representation: `Session.providerIds: List<Int>`, empty by default. No singular `providerId` field is introduced anywhere, and none is retained.

**Rationale:** there is no legacy singular field to keep compatible — the `session` table has never had a provider column, so `add-alongside` would mean inventing a singular form purely to deprecate it. TMDB's `with_watch_providers` natively accepts a comma-separated id list with OR semantics (RESEARCH.md, verified against the official reference), so the plural form maps to exactly one outbound query parameter; a singular field would have to be widened later at the cost of re-deriving the cache key, which D-07/D-09 already rate as costly. Region takes the same treatment: optional at the API, `NOT NULL DEFAULT 'DE'` at the database, so "this session has a region" is a schema guarantee and no downstream code carries a null branch.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> PUT /api/sessions/{sessionId}/filters | Untrusted caller supplies a region string and a list of provider ids that will later be forwarded into an outbound TMDB URL |
| Client -> GET /api/sessions/{sessionId}/filters | Untrusted caller reads a session's group-level filter state |
| Client -> POST /api/sessions | Unauthenticated by design (no credential exists yet at creation time) but now accepts an optional body |
| Participant -> shared session state | Any participant can mutate state that affects every other participant's deck — a deliberate group-trust model, not an oversight |
