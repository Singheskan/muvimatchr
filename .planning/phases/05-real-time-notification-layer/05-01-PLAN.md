<objective>
Replace the repo's prototype `/lobby` WebSocket layer with a real session-scoped STOMP notification layer, and prove end to end — through a real embedded server and a real STOMP client — that recording one vote pushes one status frame to a subscribed participant, carrying exactly the JSON the REST status endpoint would return.

Purpose: Phase 4 already computes `SessionVoteStatus` correctly and race-free. Nothing about this phase is allowed to recompute or reinterpret it; the only new claim is that the already-correct value reaches a connected participant without them asking. Proving that on a thin end-to-end slice first is what stops a broker-config or serialization mismatch from being discovered after three more layers are already committed.

Output: a new `realtime/` package (config + publisher), a broadcast trigger inside `VoteService.recordVote()`, the deletion of the superseded prototype WebSocket files, and a real STOMP integration test harness plus its first end-to-end proof.
</objective>

## Flagged assumptions — carried forward, not resolved

The edge-coverage probe returned `unclassified / unresolved` for all three of this phase's requirements. They are recorded here explicitly rather than converted into satisfied truths.

- **RTIME-01 — "a participant who finishes early sees a live *waiting on N of M* screen that updates as others finish."** This phase proves the server side of that sentence only: that a subscribed client receives successive status frames whose `finishedCount` and `activeCount` advance. Whether a human actually *sees* a waiting screen update is not observable until Phase 6's SPA subscribes to this topic. **Remains to be confirmed manually in Phase 6.**
- **RTIME-02 — "when the last person finishes, connected participants auto-transition to results."** This phase proves the transition *signal* is pushed (`isComplete` true with `matchedMovieIds` populated, delivered to every currently subscribed client). The transition itself is a frontend behavior. **Remains to be confirmed manually in Phase 6.**
- **RTIME-03 — "a reconnecting participant always sees correct current status, never stale."** This phase proves the server offers no stale path to reconcile against: it holds no replay buffer, and the REST status body is byte-identical in shape to the pushed body. Whether the Phase 6 client actually performs the REST fetch on every reconnect (rather than trusting a cached frame) is a frontend obligation this phase cannot enforce. **Remains to be confirmed manually in Phase 6.**

**Known limitation, deliberately accepted (ARCHITECTURE.md Pattern 4 / PITFALLS.md Pitfall 5):** the in-memory `SimpleBroker` dispatches on a pooled executor, so strict ordering between two broadcasts produced by two *simultaneously committing* votes is not guaranteed. This is why the client contract is "REST is truth, WS is a nudge." Tests in this phase drive votes sequentially and therefore assert ordered progression only under sequential finishes; ordering under a simultaneous finish is explicitly out of scope and must not be asserted.
</assumptions>

Perform the whole swap in one commit — the old and new configs cannot coexist, because both would register a STOMP endpoint at `/ws` and `SimpMessagingTemplate` only exists while some `@EnableWebSocketMessageBroker` class is present.

**1. New `org.example.muvimatchr.realtime.WebSocketConfig`.** A `@Configuration` class annotated `@EnableWebSocketMessageBroker` implementing `WebSocketMessageBrokerConfigurer`, in the new `realtime` package (not `config`).
  - `configureMessageBroker(config: MessageBrokerRegistry)` calls `config.enableSimpleBroker("/topic")` and nothing else. Do **not** carry over the application destination prefix call from the prototype: this phase is server-push only, there is no `@MessageMapping` handler anywhere in it, and an application destination prefix would only create an inbound route with no handler behind it.
  - `registerStompEndpoints(registry: StompEndpointRegistry)` calls `registry.addEndpoint("/ws")` and stops there. Register no SockJS fallback (STACK.md §"Real-Time Decision" targets modern browsers only), and leave the handshake's allowed-origin policy at Spring's same-origin default — add no origin-widening call. Widening origins for a future dev server is Phase 6's decision to make consciously, not this phase's to pre-grant.
  - `configureClientInboundChannel(registration: ChannelRegistration)` registers one `ChannelInterceptor` whose `preSend` wraps the message with `StompHeaderAccessor.wrap(message)` and returns `null` when `accessor.command == StompCommand.SEND`, and returns the message unchanged for every other command. This closes threat T-05-03: with a simple broker enabled on `/topic`, any connected client could otherwise `SEND` a forged status frame straight to `/topic/session/{someId}` and every subscriber of that session would receive it as if the server had produced it. Server-side pushes are unaffected because `SimpMessagingTemplate` publishes to the broker channel, never to the client inbound channel. Dropping the frame (returning `null`) is deliberate rather than throwing: an ERROR frame would tear down the connection and hand an unauthenticated caller a cheap way to disconnect nobody but themselves, while a silent drop is the smaller surface. Add a class comment stating that the interceptor exists because the server is push-only and that 05-CONTEXT.md D-01 defers *token* validation on CONNECT/SUBSCRIBE, which is a separate and still-open decision.

**2. New `org.example.muvimatchr.realtime.SessionEventPublisher`.** A `@Service` with a single constructor-injected `private val messagingTemplate: SimpMessagingTemplate` (Kotlin primary-constructor injection, `private val`, no `@Autowired` — matching `MatchAggregationService` and `VoteService`).
  - One public method: `broadcastStatus(sessionId: UUID, status: SessionVoteStatus)`. It maps the status with `status.toResponse()` and calls `messagingTemplate.convertAndSend("/topic/session/$sessionId", <the mapped response>)`. The destination is keyed by the session UUID per 05-CONTEXT.md D-02, matching the `/api/sessions/{sessionId}/...` REST convention rather than the 6-character join code.
  - Sending the mapped `VoteStatusResponse` rather than the raw `SessionVoteStatus` is load-bearing, not cosmetic: Kotlin generates an `isComplete()` getter and Jackson's bean introspection strips the `is` prefix, so a raw domain object would serialize the completion flag under the name `complete` while the REST endpoint emits `isComplete`. A reconnecting client reconciling REST against a remembered push would then compare two different field names — exactly the stale-state failure RTIME-03 forbids.
  - The method body must be wrapped so that no exception escapes: catch `Exception`, log at WARN including the session id, and return normally. A broadcast is best-effort UX polish and is never correctness-load-bearing (ARCHITECTURE.md Anti-Pattern 2); it must not be able to surface as a failed vote request.
  - No repository, no `MatchAggregationService`, no state field, no other public method. This class stays a dumb pipe (ARCHITECTURE.md: `realtime/` "must never own business state or be queried for vote data").

**3. Promote the response mapping in `VoteController.kt`.** Move the existing `private fun SessionVoteStatus.toResponse()` out of the `VoteController` class body and make it a top-level extension function in the same file and the same `org.example.muvimatchr.voting` package, with no visibility modifier (public). Its body is unchanged. `VoteController`'s two call sites read `status.toResponse()` / `computeStatus(sessionId).toResponse()` and stay literally identical, because same-package top-level functions need no import. This is what makes the WS payload and the REST payload the same object by construction instead of by convention.

**4. Trigger the broadcast from `VoteService.recordVote()` — after commit, once, and nowhere else.** Add `private val sessionEventPublisher: SessionEventPublisher` as a constructor parameter (import `org.example.muvimatchr.realtime.SessionEventPublisher`). Capture the existing `matchAggregationService.computeStatus(sessionId)` result into a local `val status` instead of returning it inline, then return `status` at the end.
  - Between the two, register an after-commit hook rather than broadcasting inline: if `TransactionSynchronizationManager.isSynchronizationActive()` is true, call `TransactionSynchronizationManager.registerSynchronization(...)` with an anonymous `TransactionSynchronization` overriding `afterCommit()` to call `sessionEventPublisher.broadcastStatus(sessionId, status)`; otherwise (no active transaction, which cannot happen through this `@Transactional` method but keeps the method honest if it is ever called differently) broadcast directly.
  - Why after commit and not inline: the value being pushed is a fresh read taken *inside* the still-open transaction, so an inline push would reach subscribers before the write is visible to any other connection. A client that acted on that push by fetching `/api/sessions/{sessionId}/votes/status` would read the pre-commit state under READ COMMITTED and see a lower `finishedCount` than the push it just received — the precise "stale reconciliation" outcome RTIME-03 exists to prevent. Registering after commit also guarantees a rollback can never publish a status that never became true, and that a broadcast problem cannot roll back an already-durable vote (05-PATTERNS.md's `VoteService` edit note 4).
  - `VoteService.recordVote()` is the single broadcast trigger for this phase (05-CONTEXT.md D-05). Add no second call site — in particular do not also broadcast from `VoteController`, from `MatchAggregationService`, or from any scheduled job. Idle-participant timeout transitions are deliberately not separately re-broadcast; idle status is already recomputed live on every read (04-CONTEXT.md D-07), so a screen self-corrects on the next REST fetch or the next vote's push.
  - Leave the `lockForUpdate` → `upsertVote` → `computeStatus` order and the `@Transactional` placement exactly as they are. Nothing in Phase 4's concurrency proof may be disturbed.
  - Add a short comment above the registration recording why the hook is after-commit rather than inline, so a later reader does not "simplify" it back.

**5. That page is dead prototype UI with no test coverage and no place in the Phase 6 flow; the tradeoff is recorded here rather than discovered later.
