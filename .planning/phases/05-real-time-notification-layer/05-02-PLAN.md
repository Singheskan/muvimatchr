<objective>
Expand the proven single-push slice into the three behaviors the roadmap names: a waiting client watching `finishedCount` climb, every connected client receiving the completion signal when the last participant finishes, and a client that missed messages while disconnected landing on the true current state through REST rather than on a replayed or remembered frame.

Purpose: plan 05-01 proved the pipe exists and carries the right document. This plan proves the pipe carries the right *sequence*, reaches *everyone*, and — critically — that the server deliberately offers nothing to be stale with. The "no replay on resubscribe" assertion is the one that pins ARCHITECTURE.md Pattern 4 down as an implemented property rather than an intention: it fails loudly if anyone ever adds a well-meaning last-known-state cache to the realtime layer.

Output: three added tests on the existing broadcast test class, and a new reconnect-reconciliation test class.
</objective>

The edge-coverage probe returned `unclassified / unresolved` for all three of this phase's requirements. They are recorded here explicitly rather than converted into satisfied truths. (Same three items as 05-01; repeated so neither plan can be read in isolation and miss them.)

- **RTIME-01 — "a participant who finishes early sees a live *waiting on N of M* screen that updates as others finish."** Task 1 proves the server pushes a per-vote status whose `finishedCount` advances toward `activeCount`. Whether a human sees a screen update is not observable until Phase 6's SPA subscribes. **Remains to be confirmed manually in Phase 6.**
- **RTIME-02 — "when the last person finishes, connected participants auto-transition to results."** Task 1 proves every connected client receives a completion push carrying `isComplete` true and the matched ids. The transition itself is frontend behavior. **Remains to be confirmed manually in Phase 6.**
- **RTIME-03 — "a reconnecting participant always sees correct current status, never stale."** Task 2 proves the server offers nothing stale to reconcile against: no replay on resubscribe, and a REST fetch that lands exactly on the last broadcast state. Whether the Phase 6 client actually performs that fetch on every reconnect, rather than trusting a remembered frame, is a frontend obligation this phase cannot enforce. **Remains to be confirmed manually in Phase 6.**

**Known limitation, deliberately accepted:** the in-memory `SimpleBroker` dispatches on a pooled executor, so ordering between two broadcasts produced by two *simultaneously committing* votes is not guaranteed. Task 1 therefore drives its votes strictly sequentially and asserts monotonic progression only under sequential finishes. Do not add an ordering assertion over a concurrent finish — it would be a flaky test asserting a property the architecture deliberately does not provide (ARCHITECTURE.md Pattern 4: REST is truth, WS is a nudge).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WS client → `/topic/session/{sessionId}` SUBSCRIBE | Unauthenticated subscriber, keyed only by the session UUID (05-CONTEXT.md D-01/D-02). |
| reconnecting client → `GET /api/sessions/{sessionId}/votes/status` | Authenticated reconciliation path; the bearer token is required here even though the topic is not gated. |
| broker → subscribers of one session's topic | Fan-out boundary: a payload addressed to one session must not reach another's subscribers. |
