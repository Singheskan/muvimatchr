<objective>
Turn the live status read into the two answers the phase exists to produce: which movies every currently-active participant agreed on, and how many likes each movie has.

Purpose: this is the exact logic the prior prototype got wrong. Both answers are projections of the same active-roster question, and both are computed fresh from the vote table on every call — nothing is cached, nothing is stored, nothing is sticky. The per-movie like counts are deliberately unfiltered so a ranked list can be added later without a data-model change (RSLT-03).

Output: two new native aggregate reads on `VoteRepository`, two new projections on `MatchAggregationService`, two new fields on the status response, and a behavioural test suite covering unanimity, the live roster, and the count projection.
</objective>

Add the two remaining aggregate reads and surface them through the status contract.

**VoteRepository** — add two native `@Query` reads (no `@Modifying`), binding every value through a named `@Param` exactly as the existing methods do:
- `fun findUnanimousMovieIds(@Param("sessionId") sessionId: UUID, @Param("participantIds") participantIds: Collection<UUID>, @Param("participantCount") participantCount: Int, @Param("likeChoice") likeChoice: String): List<Long>` — `SELECT v.movie_id FROM vote v WHERE v.session_id = CAST(:sessionId AS uuid) AND v.choice = :likeChoice AND v.participant_id IN (:participantIds) GROUP BY v.movie_id HAVING COUNT(DISTINCT v.participant_id) = :participantCount ORDER BY v.movie_id`. The `HAVING` comparison is an equality against the full active count — this is the whole of VOTE-04, and the equality is what makes it agreement rather than partial agreement. The `ORDER BY` is what makes the result stable across calls; the ordering must come from the database, not from re-sequencing the list in Kotlin afterwards.
- `fun findLikeCountsBySession(@Param("sessionId") sessionId: UUID, @Param("likeChoice") likeChoice: String): List<Array<Any>>` — `SELECT v.movie_id, COUNT(*) FROM vote v WHERE v.session_id = CAST(:sessionId AS uuid) AND v.choice = :likeChoice GROUP BY v.movie_id ORDER BY COUNT(*) DESC, v.movie_id ASC`. Two ordering keys, not one: a single count key leaves tied movies in an unspecified order that can differ between calls. This query takes no participant-id filter and no active-roster filter, deliberately — an idle participant's earlier likes still count toward every movie's tally (D-07), and RSLT-03's whole point is that this projection already supports a ranked list without a schema change.

**MatchAggregationService** — add two methods and fold them into `computeStatus`:
- `fun unanimousMovieIds(sessionId: UUID, activeParticipantIds: List<UUID>): List<Long>` — returns an empty list immediately when `activeParticipantIds` is empty, otherwise delegates to `findUnanimousMovieIds(sessionId, activeParticipantIds, activeParticipantIds.size, VoteChoice.LIKE.name)`. The early return is required, not defensive: an empty collection renders an empty `IN ()` list, which Postgres rejects. It is also the correct answer — with nobody present there is nothing everybody agreed on.
- `fun perMovieLikeCounts(sessionId: UUID): List<MovieLikeCount>` — maps each row of `findLikeCountsBySession(sessionId, VoteChoice.LIKE.name)` to `MovieLikeCount((row[0] as Number).toLong(), (row[1] as Number).toInt())`, preserving the order the query returned.

The empty-roster early return in `computeStatus` now also returns empty lists for both new fields, keeping the "nobody present" answer consistent across all five values.

| Boundary | Description |
|----------|-------------|

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-13 | Tampering | `findUnanimousMovieIds` / `findLikeCountsBySession` | high | mitigate | Every value bound through a named `@Param`, including the participant-id collection and the choice constant; no SQL text is assembled from caller input. |
| T-04-14 | Tampering | Roster the unanimity denominator is computed from | high | mitigate | The active roster is derived server-side from `participant.created_at` and `MAX(vote.voted_at)`; no client input contributes to it, so a caller cannot shrink the denominator to manufacture a match. |
| T-04-15 | Information Disclosure | Like counts exposed to any session member | low | accept | Counts are per movie, never per participant, so the response cannot attribute a specific vote to a specific person. Intended product behaviour and the groundwork RSLT-03 exists to provide. |
| T-04-16 | Denial of Service | Aggregate queries on every status read | low | accept | Both queries are scoped to one session and backed by `idx_vote_session_id` (V3); session sizes are small by design and the deck is capped by the pinned snapshot. No rate limiting exists app-wide — the standing accepted risk from Phases 2 and 3. |
</threat_model>
