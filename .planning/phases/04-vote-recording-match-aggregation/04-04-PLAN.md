</objective>

  <action>
Write `VoteServiceConcurrencyTest` as a `PostgresTestSupport` subclass that races real threads through `VoteService.recordVote` against real Postgres.

**Fixture per race.** Create a fresh session, join three participants, and pin a two-movie deck via `sessionService.pinDeck(sessionId, null, movies)` with hand-built `MovieCatalogService.CachedMovie` instances. Have all three participants vote on the first movie sequentially, so each is one vote short of finishing and the session is not yet complete. That first movie's votes are the setup; the race is over the second.

**The race.** Use a fixed thread pool of three and a `CountDownLatch` of one as the starting gun: each thread awaits the latch, then calls `voteService.recordVote(sessionId, participantId, secondMovieId, VoteChoice.LIKE)` and records the returned `SessionVoteStatus`. Release the latch, then await all three futures with a bounded timeout so a deadlock surfaces as a failing test rather than a hung build. Collect any thrown exception per thread and fail the test naming it, rather than letting a swallowed exception masquerade as a passing race.

**The assertions.** Exactly one of the three returned statuses has `isComplete` true — the count of true values must equal 1, asserted as an equality so both a double trigger and a missed trigger fail. All three votes for the second movie are present: a `jdbcTemplate` count of `vote` rows for that session and movie id is exactly 3. A follow-up `matchAggregationService.computeStatus(sessionId)` after the race reports `isComplete` true and `finishedCount` 3 — a race that lost a write would show a lower count here even if the per-response assertion happened to pass.

**Rule out the pool as the serialiser.** Before the race, obtain the `DataSource` bean, unwrap it to `HikariDataSource` and assert `maximumPoolSize` is at least four — one more than the racing thread count. If the pool were the bottleneck the threads would serialise there rather than in Postgres, and the test would certify a lock it never exercised. Assert this once, at the top of the test class, so its failure message names pool sizing rather than surfacing as a mysterious timeout.

**Repeat the race.** Run the whole fixture-and-race sequence over ten independently created sessions inside one test method, asserting the same invariants each time. A concurrency defect is probabilistic; a single green race is weak evidence, and ten independent races against fresh sessions is what turns this from an anecdote into a gate. Use a fresh session per iteration so a leftover lock or leftover row from one iteration cannot mask the next.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-17 | Tampering | Lost update under simultaneous final votes | high | mitigate | The session-scoped row lock serialises writers; the test asserts every racing vote is persisted and completion is reported exactly once, over ten independent races. |
| T-04-18 | Denial of Service | Lock contention degenerating into a deadlock or a stall | medium | mitigate | Futures are awaited with a bounded timeout so a stall fails the test rather than hanging the build; the transaction body contains no outbound call that could hold the lock indefinitely. |
| T-04-19 | Denial of Service | Connection-pool exhaustion masquerading as correct serialisation | medium | mitigate | The test asserts the pool carries more connections than racing threads, so a green result cannot be produced by pool-level serialisation. |
| T-04-20 | Tampering | Schema drift on restart | high | mitigate | The Flyway history row count is asserted unchanged across the restart, and `ddl-auto=validate` means the second context refuses to start if the V8 migration and the entity mapping disagree. |
